Put full pages in screens/.

4. CLEAN ARCHITECTURE AND DDD STATUS

The folder structure prepares the project for Clean Architecture; it does not itself implement architectural boundaries.
Authentication, expenses, and wallet are provisional business areas, not validated DDD bounded contexts.
Their reserved folders are:
  domain/entities/           - Future business objects with identity.
  domain/value_objects/      - Future validated values such as money or identifiers.
  domain/repositories/       - Future contracts expressed in domain terms.
  domain/use_cases/          - Future application operations requiring orchestration.
  data/models/              - Future API/storage representations and mapping.
  data/repositories/        - Future implementations of domain contracts.
  data/datasources/local/    - Future database or local-file access.
  data/datasources/remote/   - Future REST access.
  presentation/screens/     - Existing screens.
  presentation/widgets/     - Feature-specific reusable presentation.

Future dependency direction:
  Presentation calls domain contracts/use cases.
  Data implements domain contracts and maps external representations.
  Domain stays independent of Flutter widgets, HTTP clients, and storage plugins.
  App composition supplies concrete dependencies.

Keep current UI helpers embedded in their existing screen files until a separate code-refactoring task is authorized.
For example, WalletTextField and AccountOptionTile remain in connect_wallet_screen.dart.
An existing dependency remains from the shared header to decorative helper classes in home_screen.dart.
Existing feature-to-app-shell references also remain.
These dependencies were preserved to honor the folder-only scope and should be resolved in a future architecture implementation pass.
No entities, aggregates, value objects, repositories, use cases, or synchronization rules have been implemented by this delivery.
